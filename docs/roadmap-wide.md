## 1. Крипто-идентичность вместо короткого random id `[расширить]`

**Цель.** ID = публичный ключ (или стабильный fingerprint), создаётся офлайн.

**Работы.**

- Выбрать алгоритм (например Ed25519 / Web Crypto ECDSA P-256).
- Генерация пары, хранение приватного ключа (IndexedDB / OPFS / позже OS keystore в Tauri).
- Миграция с текущего `profile.id` (8–24 chars): alias, dual-id период, или hard cut.
- Подпись/проверка произвольных payloads (профиль, invite, presence).

**Готово когда:** офлайн создаётся личность; второй клиент проверяет подпись карточки; старые контакты либо мигрированы, либо явно помечены.

**Вопросы для закрытия пункта**

1. Какой алгоритм и формат pubkey в UX (hex / base58 / multibase)?
2. Делаем seed-фразу (BIP39) для восстановления или только экспорт файла ключа?
3. Что с уже разданными короткими id и карточками `C1.` — совместимость или breaking change?
4. Где хранить ключ в PWA, чтобы iOS/Android не сносили при чистке (и что делать если снесут)?

## 2. Подписанный профиль и локальная адресная книга `[расширить]`

**Цель.** Имя/аватар «приклеены» к ключу подписью; локальный alias важнее глобального ника.

**Работы.**

- Схема профиля: `{ pubkey, nick, avatarRef|data, updatedAt, sig }`.
- Локальные поля контакта: `localAlias`, `trust` (met-in-person / introduced / unverified).
- UI: показать alias, глобальный ник мелким; «переименовать у себя».
- Карточка обмена: минимум pubkey (+ опционально hint реле); аватар подтягивается отдельно.

**Готово когда:** смена глобального ника не ломает ваш alias; подделка ника без ключа отбрасывается.

**Вопросы для закрытия пункта**

1. Аватар: data-URL как сейчас, или хэш/IPFS/релей-blob с лимитом размера?
2. Нужны ли статусы доверия в UI (метка «видели лично»)?
3. Группы контактов остаются? Как идентифицируем группу без центра?
4. Можно ли скрыть глобальный ник полностью, если есть alias?

## 3. Обмен «это я» и пересылка чужого контакта `[расширить]`

**Цель.** Первая встреча QR/paste; потом «сарафан» — переслал pubkey друга, профиль догрузился.

**Работы.**

- Invite: свой pubkey + актуальные relay hints + короткая подпись.
- Introduce: сообщение/карточка чужого pubkey (+ известные реле); без копирования аватара как истины.
- После получения — fetch профиля с реле/DHT и verify sig.
- Защита от подмены: новый ключ с тем же ником = новый незнакомец.

**Готово когда:** A знакомит B с C по карточке; у B появляется контакт C с актуальным ником после verify.

**Вопросы для закрытия пункта**

1. Introduce только вручную (кнопка) или ещё из чата/звонка?
2. Нужен ли TTL / одноразовый токен на invite, или pubkey+hint достаточно навсегда?
3. Offline introduce (только QR без сети) — обязателен в первой очереди?
4. Сколько relay hints класть в QR, чтобы не раздуть код?

## 4. Модель реле: дом, гости, пучок запасных `[новое` / расширить servers]

**Цель.** Клиент может сесть на любой живой узел; узел отдаёт N адресов; список живёт в кэше.

**Работы.**

- Контракт реле: register(pubkey, presence) · signal · peer-list · optional STUN/TURN advertise.
- Bootstrap seed-список в клиенте + user overrides (экран «Серверы»).
- Ответ «пучок» 10–15; выкидывать мёртвые; перемешивать.
- Мульти-подключение: 1..K активных реле одновременно (presence на нескольких).
- Совместимость с текущим `server/` (комнаты `c-{id}`) — эволюция протокола.

**Готово когда:** клиент без ручного URL (кроме первого seed) набирает пучок и держит presence хотя бы на одном узле.

**Вопросы для закрытия пункта**

1. Релей пишет ли pubkey→комнату в свою БД или только эфемерный RAM как сейчас?
2. Сколько одновременных реле в MVP (1 / 3 / 5)?
3. Обязательна ли авторизация на реле (подпись challenge) с первого дня?
4. Публикуем ли мы официальные seed-узлы или только self-host + LAN?

## 5. Discovery после смены сервера `[новое]`

**Цель.** Если оба переехали — всё равно найтись: редирект · прямой обмен · (позже) DHT.

**Работы.**

- Записка на старом реле: signed `{ pubkey → newRelays[] }`, TTL.
- Клиент при fail стучится в last-known + спрашивает редирект.
- UX «потеряли друг друга» → покажи QR / скопируй новый адрес.
- Фаза 2: DHT/libp2p или упрощённый shared directory между реле (без обещания полного IPFS в браузере сразу).

**Готово когда:** сценарий «A и B сменили реле» восстанавливается хотя бы через редирект или повторный QR; план DHT записан отдельно.

**Вопросы для закрытия пункта**

1. DHT в первой поставке или явно phase-2 после пучка+редиректа?
2. Если берём libp2p — браузер только клиент к десктоп-ноде, или wasm в PWA тоже?
3. Сколько хранить редиректы на реле (время/квота)?
4. Нужен ли «общий» публичный directory как опция (слабее цензуростойкость)?

## 6. WebRTC-звонок (голос → видео → экран) `[есть UI / добить media]`

**Цель.** Личная звонилка поверх того же identity и signaling router.

**Работы.**

- `getUserMedia` audio; отдельный PeerConnection или общий с DataChannel — решить.
- Сигналинг SDP/ICE через реле-пучок (не один hardcoded URL).
- UI: исходящий/входящий, отказ, busy, reconnect.
- Видео и `getDisplayMedia` следующим подпунктом.
- Честный fail: нет пути → предложи TURN из пучка / свой.

**Готово когда:** два устройства звонят голосом end-to-end по WebRTC после стука/из контактов.

**Вопросы для закрытия пункта**

1. Один PC на звонок+файлы или раздельные соединения?
2. Групповые звонки в горизонте или строго 1:1?
3. Запись звонка / голосовые сообщения — нужно ли вообще?
4. Нужны ли кодек-предпочтения / шумодав на первом этапе?

## 7. STUN/TURN из пучка и антиабьюз `[расширить]`

**Цель.** Узлы из пучка могут отдавать STUN; TURN — явный/свой; защита от спама запросов.

**Работы.**

- Реклама ICE URL в peer-list / capability flags.
- Не подставлять чужой TURN молча; UI показывает `relay` path.
- PoW или rate-limit+signed challenge перед выдачей TURN credentials / тяжёлым signaling.
- Документация: домашний узел как TURN для друзей.

**Готово когда:** звонок при жёстком NAT проходит через выбранный TURN; без PoW/лимита узел не раздают в проде.

**Вопросы для закрытия пункта**

1. PoW сразу или сначала IP rate-limit + подпись pubkey?
2. TURN credentials: долгоживущие user/pass или short-lived (TURN REST)?
3. Может ли PWA быть TURN? (обычно нет) — только десктоп/VPS?
4. Кто платит трафик домашнего TURN — только owner allowlist друзей?

## 8. Presence, стук, «доступен» — на ключах `[расширить]`

**Цель.** Текущая модель лобби переезжает на pubkey; стук инициирует звонок/сессию файлов.

**Работы.**

- Лобби id от fingerprint pubkey (стабильный, не короткий random).
- Presence на K реле; агрегировать «онлайн если виден хоть где-то».
- Knock → accept → media или transfer.
- Wake Lock / visibility — сохранить поведение из `features-realtime.md`.

**Готово когда:** книга показывает онлайн по новым id; стук поднимает звонок или передачу.

**Вопросы для закрытия пункта**

1. Онлайн = «в любом реле из моего пучка» или «в пересечении с его advertised»?
2. Скрытый режим / last seen — нужны ли?
3. Очередь стуков, если занят на другом звонке?
4. Push-уведомления вне вкладки — в scope или нет (PWA limits)?

## 9. E2EE сообщения и локальное хранение `[новое]`

**Цель.** Переписка только локально по умолчанию; на проводе — сильное шифрование.

**Работы.**

- Выбор примитива: готовый Signal-протокол (lib) vs упрощённый sealed box на первом этапе.
- Хранилище: OPFS/IndexedDB; ключи сессий отдельно от identity seed.
- UI чата минимальный (1:1) или отложить после звонка — по scope п.0.
- Сервер видит только ciphertext / routing envelope.

**Готово когда:** сообщение A→B не читается реле; история на устройстве переживает перезапуск PWA (в пределах политики браузера).

**Вопросы для закрытия пункта**

1. Чат в MVP-2 или после стабильных звонков?

3. Исчезающие сообщения / TTL — нужно?
4. Вложения в чате = тот же transfer protocol или отдельно?

## 10. Синхронизация между своими устройствами `[новое]`

**Цель.** Настройка: без синка · P2P устройство↔устройство · зашифрованный бэкап на реле.

**Работы.**

- Pairing второго устройства (QR с одноразовым secret).
- Режим 2: WebRTC sync cursors истории.
- Режим 3: encrypted blob на реле, decrypt только ключом пользователя.
- Явные предупреждения про потерю ключа / кэша PWA.

**Готово когда:** пользователь выбирает режим; по умолчанию — самый безопасный (локально only).

**Вопросы для закрытия пункта**

1. Какой default: только локально или P2P sync?
2. Один identity на много устройств или device keys + linking (как Signal)?
3. Бэкап seed/фразы в UX обязателен до включения облачного blob?
4. Синкаем ли файлы inbox или только чат/метаданные?

## 11. Десктоп-приложение как нода `[новое]`

**Цель.** Win/Linux/Mac (Tauri предпочтительно): тот же UI-код + системный DHT/TCP/TURN.

**Работы.**

- Общее TS-ядро; thin native layer для сокетов/файлов/автостарта.
- Режим «сделать этот ПК моим реле».
- PWA находит домашний узел (LAN mDNS / QR / сохранённый URL).
- Устойчивое хранение ключей вне IndexedDB.

**Готово когда:** ПК-нода в LAN обслуживает signaling+STUN для телефона того же пользователя; ключ не теряется при очистке браузера.

**Вопросы для закрытия пункта**

1. Tauri или Electron (вес vs скорость выхода)?
2. Нода шарит только владельцу или может быть relay для друзей (allowlist)?
3. Нужен ли system tray / автозапуск сразу?
4. Мобильные store-обёртки (Capacitor) в том же пункте или никогда?

## 12. Устойчивость к блокировкам и UX «магия без настройки» `[новое]`

**Цель.** Пользователь не вводит IP; клиент сам перебирает пучок и запасные пути.

**Работы.**

- Политика выбора маршрута (latency, success rate, «адресат виден здесь»).
- Фоновый healthcheck реле.
- Понятные статусы: ищем путь / прямой / через TURN / потеряли контакт → QR.
- Опционально: мост через третьего онлайн-друга (осторожно с abuse).

**Готово когда:** при падении одного реле звонок/presence восстанавливаются без ручного экрана «Серверы».

**Вопросы для закрытия пункта**

1. Разрешаем ли «невидимый мост» через третий клиент в MVP или это этически/юридически later?
2. Нужен ли ручной pin «всегда через мой VPS» поверх авто?
3. Логи диагностики для пользователя — какой уровень детализации?
4. Метрики анонимно себе (opt-in) или никогда?
